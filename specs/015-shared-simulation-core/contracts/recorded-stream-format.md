# Contract: Recorded stream `MMRS` (format version 1)

A recorded stream is one case of the agreement suite. It holds the format version, the rules
revision, the step rate, the configuration, the collision data's checksum, the seed and match salt,
the initial state, every input command in order, and the expected state hash after every step
(FR-022). The extension is `.mmrs`.

- **Committed streams.** The 18 named scenario streams live in `simcore/streams/`: `flat-run-20hz`,
  `flat-run-30hz`, `flat-run-60hz`, `wall-slide-45`, `stairs-climb`, `stairs-blocked`,
  `slope-limit`, `jump-land`, `crouch-under-ledge`, `corner-wedge`, `thin-wall-fast`, `rifle-burst`,
  `launcher-arc`, `reload-and-empty`, `heat-overheat`, `projectile-hits-hitbox`,
  `mesh-occludes-shot` and `fuzz-all-buttons` (one seeded fuzz stream). They are written only by
  `simcore streams record`, and their expected hashes come from the server build (see
  [Regeneration](#regeneration)).
- **Generated streams.** The 50 seeded streams (seeds 1 to 50) are generated by `StreamGenerator`
  into the agreement suite's work directory at test time and are never committed (US2 scenario 3).
- **What version 1 pins.** This layout, the config block's field table
  ([config-rules.md](config-rules.md#field-ids)), canonical state serialisation version 1
  ([state-serialization.md](state-serialization.md)) and input command version 1
  ([input-command-format.md](input-command-format.md)). Changing any of them is a new format
  version. The step rules are pinned separately by the rules revision.

Rules shared with the other formats: little-endian everywhere through `BinaryPrimitives`; floats as
exact binary32 bits; nothing allocated before every count is bounded; no partial result returned on
a refusal (US6 scenario 3).

## Layout

### Header (64 bytes)

| Offset | Size | Type | Field | Rule |
| --- | --- | --- | --- | --- |
| 0 | 4 | ASCII | `magic` | `MMRS` (`4D 4D 52 53`) |
| 4 | 2 | u16 LE | `version` | 1 |
| 6 | 2 | u16 LE | `headerLength` | 64 |
| 8 | 4 | u32 LE | `rulesRevision` | the `SimCoreVersion.RulesRevision` the stream was recorded with; checked when the stream is opened to run |
| 12 | 2 | u16 LE | `stepHz` | [20, 60]; equals the config block's `stepRateHz` |
| 14 | 2 | u16 LE | `characterCount` | [1, 64]; equals the initial state's `characterCount` |
| 16 | 4 | u32 LE | `stepCount` | [1, 2²⁰] |
| 20 | 8 | u64 LE | `seed` | the seed the stream's commands were generated from (a generated stream, or a seeded scenario such as `fuzz-all-buttons`); 0 for a scenario stream with no seed |
| 28 | 8 | u64 LE | `matchSalt` | given to the world with the initial state; an input to every shot's spread (FR-008) |
| 36 | 8 | u64 LE | `collisionChecksum` | the trailer checksum of the collision data the stream was recorded against (FR-021) |
| 44 | 4 | u32 LE | `configLength` | ≤ 65,536 |
| 48 | 4 | u32 LE | `initialStateLength` | ≤ 1 MiB (1,048,576) |
| 52 | 4 | u32 LE | `stepsLength` | the steps block's byte length |
| 56 | 8 | u64 LE | `fileLength` | the whole file, trailer included; must equal the actual length; ≤ 64 MiB |

Total: 64 bytes (4 + 2 + 2 + 4 + 2 + 2 + 4 + 8 + 8 + 8 + 4 + 4 + 4 + 8).

### Blocks

| Offset | Size | Type | Field | Rule |
| --- | --- | --- | --- | --- |
| 0 | 64 | header | header | above |
| 64 | `configLength` | config block | `config` | [below](#config-block) |
| 64 + `configLength` | `initialStateLength` | canonical state | `initialState` | [below](#initial-state) |
| 64 + `configLength` + `initialStateLength` | `stepsLength` | steps block | `steps` | [below](#steps-block) |
| `fileLength` − 8 | 8 | u64 LE | `checksum` | XxHash64, seed 0, of bytes [0, `fileLength` − 8) |

```text
fileLength = 64 + configLength + initialStateLength + stepsLength + 8
```

### Config block

The binary form of the whole configuration. Field IDs, kinds, paths and ranges are the rule table in
[config-rules.md](config-rules.md); `ConfigBlock` (`src/MmoEngine.SimCore/Config/`) reads and writes
it.

| Offset (in the block) | Size | Type | Field | Rule |
| --- | --- | --- | --- | --- |
| 0 | 2 | u16 LE | `count` | the number of entries |
| 2 + 6k | 2 | u16 LE | `entries[k].fieldId` | `section << 12 \| instance << 8 \| field`; a field of the table; strictly ascending |
| 4 + 6k | 4 | u32 LE | `entries[k].valueBits` | Int: the `int`'s two's complement bits; Enum: the member's value; Float: the `float`'s bits |

Total: 2 + 6·`count` bytes, which must equal the block's length.

- **Complete.** Every field of every present instance appears exactly once. The weapon instances
  present are slots 0 to N − 1 with no gap, and likewise the projectile classes; the general,
  movement, both hitbox stances and input sections are always complete.
- **Structure only.** The block decoder checks the structure, not the values. A value outside its
  range, or a float that is NaN, decodes, and the guard refuses it when the stream is opened, with
  the field's path and message (FR-029). Keeping every value rule in the one guard means a stream
  and a JSON file are refused for the same reasons.
- **Size.** The placeholder configuration (`simcore/config/default.json`: two weapons, two
  projectile classes) has 116 entries, so its block is 698 bytes. The table has at most 260 fields,
  so a block is at most 1,562 bytes; the 64 KiB limit is a backstop.
- **Standalone.** `BatchStepper.LoadConfig` takes the same block on its own. There its errors have
  format `config` and offsets from the block's first byte, for example
  `config entries[3].fieldId at offset 20: ...`. Inside a stream they have format `stream`, file
  offsets, and the field prefixed by `config.`.

### Initial state

The canonical state with all six event counts 0 ([state-serialization.md](state-serialization.md)).
Its `step` field is the stream's starting step S₀; the first step entry is S₀ + 1. The stream
decoder reads it with the byte-only checks of [Loading a
state](state-serialization.md#loading-a-state). The checks that need the configuration and the
collision world run when the stream is opened. Its errors have format `stream`, file offsets, and
the field prefixed by `initialState.`.

With every stream limit at its maximum (64 characters, 8 weapons each, 16,384 projectiles) an
initial state is 821,528 bytes, so the 1 MiB limit never refuses a valid one.

### Steps block

`stepCount` entries, back to back:

| Offset (in the entry) | Size | Type | Field | Rule |
| --- | --- | --- | --- | --- |
| 0 | 4 | u32 LE | `steps[i].step` | S₀ + i + 1 |
| 4 | 1 | u8 | `steps[i].commandCount` | ≤ `characterCount` |
| 5 + 18c | 1 | u8 | `steps[i].commands[c].characterIndex` | below `characterCount`; strictly ascending within the step |
| 6 + 18c | 17 | input command | `steps[i].commands[c].input` | [input command v1](input-command-format.md); decoded, not validated |
| 5 + 18·`commandCount` | 8 | u64 LE | `steps[i].expectedHash` | the state hash after this step (FR-022) |

Total per entry: 13 + 18·`commandCount` bytes (31 with one command, 13 with none). The entries must
fill the block exactly.

- **Character index.** The position in the world's character list, in ascending character ID.
  Characters neither join nor leave during a stream.
- **One command per character per step at most.** A character with no command in a step is stepped
  with the neutral input ([data-model.md](../data-model.md)).
- **Commands are not validated here.** A command the validator would reject (a repeated sequence,
  reserved button bits, a pitch out of range) decodes, and the world rejects it at that step and
  records the rejection in the hashed events. This is how the streams exercise US1 scenario 9; the
  `fuzz-all-buttons` stream sets every button bit, reserved bits included.
- **Embedded errors.** A command that fails to decode is reported with the input codec's code, at
  its file offset, with the field prefixed, for example `steps[3].commands[0].input.version`.

## Decoding

`RecordedStream.Decode` runs these checks in order and throws `CoreFormatException` at the first
failure. Steps 1 to 6 read only the header and allocate nothing.

| # | Check | Code | Offset | Field |
| --- | --- | --- | --- | --- |
| 1 | at least 4 bytes; then `magic` is `MMRS` | `Truncated`; `UnknownMagic` | the length; 0 | `magic` |
| 2 | at least 6 bytes; then `version` is 1 | `Truncated`; `UnsupportedVersion` | the length; 4 | `version` |
| 3 | at least 8 bytes; `headerLength` is 64; at least 64 bytes | `Truncated`; `Inconsistent`; `Truncated` | the length; 6; the length | `headerLength`; `headerLength`; `header` |
| 4 | the actual length equals `fileLength`: fewer bytes, or more | `Truncated`; `Oversized` | the actual length; `fileLength` | `fileLength` |
| 5 | limits: `fileLength` ≤ 64 MiB; `configLength` ≤ 65,536; `initialStateLength` ≤ 1 MiB; `characterCount` in [1, 64]; `stepCount` in [1, 2²⁰] | `Oversized` above a limit, `OutOfRange` for a zero count | 56, 44, 48, 14, 16 | that field |
| 6 | 64 + `configLength` + `initialStateLength` + `stepsLength` + 8 equals `fileLength`, in checked `u64` arithmetic | `Inconsistent` | 56 | `fileLength` |
| 7 | the trailer equals the XxHash64 (seed 0) of [0, `fileLength` − 8) | `ChecksumMismatch` | `fileLength` − 8 | `checksum` |
| 8 | `stepHz` in [20, 60] | `OutOfRange` | 12 | `stepHz` |
| 9 | the config block: length 2 + 6·`count` (fewer bytes, or more); each `fieldId` known and above the one before; every field present | `Truncated`, `Oversized`; `Inconsistent` | where the block and the count part, or the entry's offset, or for a missing field the offset where it would sort | `config.count`; `config.entries[k].fieldId`; `config.<path>` for a missing field |
| 10 | `stepHz` equals the config's `stepRateHz` | `Inconsistent` | 12 | `stepHz` |
| 11 | the initial state: the byte-only checks, then its `characterCount` equals the header's | as in [Loading a state](state-serialization.md#loading-a-state); `Inconsistent` | the field's offset | `initialState.<path>` |
| 12 | each step entry in order: `step`, `commandCount`, then each command's index and input; the entries fill the block exactly | `Inconsistent` (step number, command count, ascending index, block fill); `OutOfRange` (index); the input codec's codes | the field's offset | `steps[i].<path>` |

- The version is checked before any other field, so a stream from another version is refused as
  `UnsupportedVersion` naming both versions, whatever its length (US2 scenario 5, US6 scenario 2).
- The checksum comes before the values, so a corrupted file is refused as corrupted. A test that
  needs to reach a value check rewrites the trailer first (`fixChecksum`).
- Decoding does not check the rules revision, the collision data or the configuration's values.
  Those belong to opening the stream, below. A format fixture therefore stays decodable when the
  step rules change.

Messages have the shape `"<format> <field> at offset <n>: <detail>"`, with format `stream`:

```text
stream version at offset 4: unsupported version 2; this reader supports version 1
stream fileLength at offset 56: the blocks need 951 bytes; fileLength is 950
stream config.entries[1].fieldId at offset 72: field 0x0001 is not above 0x0002
stream config.input.weaponSlots at offset 756: field 0x5001 is missing
stream steps[0].commands[0].input.version at offset 905: unsupported version 2; this reader supports version 1
```

## Opening a stream to run

`StreamRunner` opens a decoded stream in this order. Every refusal happens before the first step
runs (US6 scenario 5).

| # | Check | Refusal |
| --- | --- | --- |
| 1 | `RecordedStream.Decode` | `CoreFormatException`, as above |
| 2 | `rulesRevision` equals `SimCoreVersion.RulesRevision` | `CoreFormatException` with `RulesRevisionMismatch`, offset 8, field `rulesRevision`: `rules revision 1 in the stream; this core implements rules revision 2` |
| 3 | one of the supplied collision worlds has `Checksum` equal to `collisionChecksum` | `CoreFormatException` with `CollisionDataMissing`, offset 36, field `collisionChecksum`: `collision data 9224e3fa3b3fca9c was not supplied` |
| 4 | `CompiledConfig.Create(stream.Config)` | `ConfigValidationException` with every `ConfigError` (path and message), not a format error ([config-rules.md](config-rules.md#recorded-streams)) |
| 5 | `SimWorld.Reset(initialState, matchSalt)`: the checks that need the configuration and the world | `CoreFormatException`, format `stream`, field `initialState.<path>` |

Then each step entry runs as one `SimWorld.Step` with its commands, and produces one step record
([state-serialization.md](state-serialization.md#step-record)). A step fault stops the run with
`StepFaultException` (`step <n> faulted: <code> at <path>`; [wasm-api.md](wasm-api.md#streamrunner)).
Expected hashes are not checked while running; the caller compares them.

**The rules revision.** `SimCoreVersion.RulesRevision` (`u32`, starts at 1) names the step rules:
every rule, algorithmic constant and reason code in [data-model.md](../data-model.md). A change that
can alter any step's result bumps it in the same commit. A stream recorded under another revision is
not compared at all: its expected hashes were produced by other rules, so a mismatch says nothing
about agreement. The suite reports it as **NotComparable**, naming both revisions, and never as a
divergence (US2 scenario 5; the same convention as the harness's [golden
runs](../../014-telemetry-test-harness/contracts/golden-run.md)). Revision 0 is never valid.

**The collision lookup.** The caller supplies the collision worlds it has: `simcore` loads the files
it is pointed at, and the browser runner loads the file the agreement manifest names. The stream is
matched by checksum, never by file name, so a stream cannot run against other collision data.
Regenerating `simcore/content/test-world.mmcd` with different content changes its checksum, and
every committed stream is then refused with `CollisionDataMissing` until it is recorded again.

### Outcomes

`simcore streams verify` gives each stream one outcome. `simcore agreement compare` uses the same
names: Match and Diverged per build and stream (a build that refuses a stream the server ran is
Diverged), and NotComparable for a work directory prepared under another rules revision or format
version. A stream the server build refuses fails `agreement prepare` instead
([simcore-cli.md](simcore-cli.md#agreement-prepare)).

| Outcome | When |
| --- | --- |
| Match | every step's record equals the server build's and its hash equals the expected hash |
| Diverged | some step differs: the report names the stream, the first divergent step, the build and every differing field ([divergence report](state-serialization.md#divergence-report)) |
| NotComparable | the stream's format version or rules revision differs from the core's; the report names both values |
| Refused | any other refusal while decoding or opening (a format error, `CollisionDataMissing`, an invalid configuration, an initial state the world refuses) |

Only Match passes. The exit codes are in [simcore-cli.md](simcore-cli.md).

## Regeneration

Expected hashes change only through a committed regeneration that states why (FR-028):

- **One writer.**
  `simcore streams record --scenario <name>|--all --out simcore/streams --reason "<why>"` is the
  only code that writes `.mmrs` files under `simcore/streams/`. It runs the server build, writes the
  core's current `SimCoreVersion.RulesRevision` into every stream it records, prints each stream's
  old and new hash, and appends the reason to `simcore/streams/REGENERATIONS.md`. Without `--reason`
  it exits 2 and writes nothing ([simcore-cli.md](simcore-cli.md)).
- **Tests never write.** Tests and `simcore streams verify` open stream files read-only
  (`FileAccess.Read`). `simcore agreement prepare` copies the committed streams into its work
  directory and writes the generated ones there. An architecture test checks that only the
  `streams record` command handler calls the stream file writer.
- **A rules change.** The commit that changes the rules bumps `SimCoreVersion.RulesRevision`. Until
  the streams are recorded again, `streams verify` reports every stream NotComparable and fails, so
  the regeneration and its reason land in the same pull request.

## API

```csharp
// src/MmoEngine.SimCore/Formats/RecordedStream.cs (namespace MmoEngine.SimCore.Formats)
public sealed class RecordedStream
{
    public const ushort FormatVersion = 1;
    public const int HeaderLength = 64;
    public const long MaxFileLength = 64L * 1024 * 1024;
    public static ReadOnlySpan<byte> Magic => "MMRS"u8;

    public uint RulesRevision { get; }
    public int StepHz { get; }
    public int CharacterCount { get; }
    public ulong Seed { get; }
    public ulong MatchSalt { get; }
    public ulong CollisionChecksum { get; }
    public SimConfig Config { get; }
    public ReadOnlyMemory<byte> InitialState { get; }   // canonical state bytes
    public IReadOnlyList<RecordedStep> Steps { get; }

    // Every decoding check above. Throws CoreFormatException; never returns a partial stream.
    public static RecordedStream Decode(ReadOnlySpan<byte> bytes);

    // Computes the block lengths, fileLength and the trailer, then decodes the result,
    // so it throws exactly what Decode would.
    public byte[] Encode();
}

public sealed record RecordedStep(uint Step, RecordedCommand[] Commands, ulong ExpectedHash);
public readonly record struct RecordedCommand(byte CharacterIndex, InputCommand Command);

// src/MmoEngine.SimCore/SimCoreVersion.cs (namespace MmoEngine.SimCore)
public static class SimCoreVersion
{
    public const uint RulesRevision = 1;
}
```

`StreamRunner` (`src/MmoEngine.SimCore/Batch/`) opens and runs a stream as above; its entry points,
including the browser's `RunStream`, are in [wasm-api.md](wasm-api.md). Decoding is not on the tick
path and may allocate.

## Golden fixtures

`simcore/golden/stream/`, under the [shared fixture
rules](input-command-format.md#shared-fixture-rules). These fixtures pin the byte format. Their
expected hashes are values like any other field (`0000000000000001`, `0000000000000002`, …) and are
not checked against a run; the committed streams in `simcore/streams/` pin behaviour. A valid case's
JSON holds the header fields, `config` as its entries
(`{ "fieldId": "0x1007", "path": "movement.gravity", "valueBits": "0x411CF5C3" }`),
`initialStateHex` (the canonical state's bytes, whose layout the worked example in
[state-serialization.md](state-serialization.md#worked-example) pins), and `steps`, each with its
`step`, its `commands` (`characterIndex` and the command's fields) and its `expectedHash`.

The base of the refusal cases.

### Other valid cases

| Case | What it pins |
| --- | --- |
| `two-characters` | two characters (IDs 1 and 4); step 1 has commands for indices 0 and 1, step 2 only for index 1 |
